# Report relay

The small Cloudflare Worker that receives reports from "Report a problem" (see [PRIVACY.md](../PRIVACY.md)).

- `src/worker.js`: the whole service. It stores the report file in Cloudflare R2 and opens an entry in a private GitHub repository. The connecting IP is only used, scrambled under a key that is replaced daily, to limit reports per hour; it is never written anywhere.
  - Retention: an hourly job deletes every report older than 60 days (`KEEP_DAYS`; the bucket's lifecycle rule is a second net) and retires its GitHub entry: deleted when the token has the rights, otherwise emptied, closed and locked. The player's typed text is not copied into the entry (`ISSUE_PLAYER_TEXT`), because GitHub keeps an edited entry's earlier text in its history.
  - Intake filters: a report from a test build (build `test` or `smoke`) is refused with 403 and nothing is stored. A report from MA2 Report.exe that holds nothing (no text, no install, no logs: the zip has only `system.txt`, as sent by automated sandboxes that run the helper on its own) is stored like any other but opens no GitHub entry and no conversation.
  - `DELETE /v1/report/<id>` (owner key) deletes one report and its entry on request (`python tools/triage.py delete MA2-XXXXXX`).
  - `GET /v1/latest` answers the game's once-per-start update check and the installer's "Update to X" with the newest release: its version and, for the installer, the SHA-256 and size of the release's installer file. It reads nothing from the request.
  - The newest release is set after a GitHub release is published with `python tools/triage.py announce X.Y.Z --installer <the release's installer exe>` (it checks the GitHub release first, shows a summary and asks; `--show`, `--undo`). It is stored in the bucket (`config/latest.json`), so no dashboard step or redeploy is needed; the `LATEST_*` vars apply only while nothing was announced.
  - Report conversations (1.2.0): a 1.2.0 client sends a random key (`reply_secret`) with its report; the service keeps only its SHA-256 in `conv/<id>.json`, next to the developer's replies and the player's answers (plain text, at most 1000 characters each; answers may carry a new report file in `answers/<id>/<n>.zip`). `POST /v1/replies` gives a key holder the replies not seen yet (it sends only report numbers and keys, rate-limited per connection like reports, no IP stored); `POST /v1/answer` takes the answer to the developer's newest reply (same limits as a report) and posts it as a comment on the report's private issue. Everything of a report is deleted 60 days after its **last** message: the hourly job reads `last` from each conversation, keeps an active one (and re-writes its files once they are 45 days old, so the bucket's 60-day lifecycle rule never reaches them), and deletes an ended one with its comments. A report without a key (1.1.x) works exactly as before, without replies. `GET /v1/latest` has nothing to do with any of this.
  - `GET /v1/open/<id>` shows the developer the conversation (oldest first) with the download link and a reply box; a reply can be edited until the player has seen it. `triage.py conversations | conversation | reply | get-logs` do the same from a console.
- `wrangler.toml` / `wrangler.staging.toml`: the deploy settings. Workers Logs is off (`[observability] enabled = false`). Secrets (the GitHub token and the owner key) are never in these files.
- `GET /v1/open/<id>` (the Download link in each issue): asks the developer for the owner key once per browser, then sets a cookie that only allows downloading reports and, from 1.2.0, reading and replying to their conversations (`HttpOnly`, `Secure`, `SameSite=Lax`; derived from the key, so changing the key signs every browser out). Every other owner action still needs the key in a header.
- `tools/triage.py`: the developer's tool for reading reports (also `delete`, `expire`, `draft-issue`); it uses the production relay by default and can keep the owner key in Windows Credential Manager. `tools/ma2_reports.pyw`: the developer's one-click helper (report number on the clipboard -> downloaded, summarised, folder opened). `tools/smoke.py`: deploy checks.
- Deploys run from `.github/workflows/relay-deploy.yml`: tests, staging, then production after the owner approves.
- `test/`: `node --test test/relay.test.mjs`, `node --test test/intake.test.mjs`, `python test/test_triage.py` and `python test/test_announce.py`.
